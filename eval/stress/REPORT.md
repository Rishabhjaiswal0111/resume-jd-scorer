# Stress test and code review: JD × resume scorer

*2026-11-17 · branch `feat/phase-1-core-pipeline` · engine 1.2.0 · prompts `jd_parse.v2` / `evaluate.v2`*

## TL;DR

- **The scoring engine is solid.** Over 1,560 full-scale scored pairs and 108 session-graded pairs, every run replayed to an identical score, no run failed when the DB pool was big enough, and the outcome rules (knock-outs → "Not eligible", screening items → "Unknown", group relief, caps) behaved as specified.
- **Two concurrency bugs will hit real users:**
  1. **15 simultaneous first-time scoring requests all fail** after a 30 s DB pool timeout.
  2. **Scoring several resumes in parallel against the same new JD fails 4 out of 5 times** with a unique-constraint error, and every one of those requests still pays for a JD parse.
- **PII redaction has 6 bugs that change what the model sees,** for example job dates replaced by `[PHONE]`, "Ruby on Rails" turned into `[CANDIDATE] on Rails`, and accented names sent to the LLM unredacted. **16 of the 104 test resumes** are affected.
- **The model is never told today's date,** yet the prompt asks it to compute years from "Present".
- **No real-model run yet.** `.env` has no `ANTHROPIC_API_KEY`, and you asked to use the Claude Code session as the model. So real grading was checked on a 36-pair sample graded by this session. Haiku's run-to-run variance is still unmeasured; the commands to measure it are at the end.

## Findings

Ranked by impact. The probe or run that confirmed each one is named in the text.

### 1. DB pool starvation when a JD is new (high)

**Where:**
- [rubric_service.py:33-38](../../backend/app/services/rubric_service.py#L33-L38), called from [scoring_service.py:95](../../backend/app/services/scoring_service.py#L95)

**What happens:**
- `latest_for_jd` runs a SELECT on the request's session. That opens a transaction, and the connection stays checked out, idle in that transaction, for the whole JD-parse LLM call (up to 90 s × 4 attempts).
- During the call, the LLM client's price lookup and ledger each need another connection.
- With the default pool (5 + 10 overflow), 15 concurrent first-time requests hold all 15 connections and then wait for a 16th. All of them time out after 30 s.

**Evidence:**
- [`concurrency_probe.py`](concurrency_probe.py) drives the real `ScoringService.score_pdfs` path: 15 concurrent requests → 15 × `TimeoutError: QueuePool limit … reached`.
- The same failure appeared as 80 of 104 JD parses lost in run `o3_pool5`.

**Fix:**
- End the transaction before the LLM call: `await session.commit()` after the cache lookup and `load_text`, before `parse_jd`. With `expire_on_commit=False`, `jd` stays usable.
- Add a regression test at concurrency > `pool_size + max_overflow`.
- Raising `db_pool_size` only moves the cliff.

### 2. Parallel requests for the same new JD fail (high)

**Where:**
- the same function: `next_version()` + insert, with constraint `uq_rubrics_jd_document_id_version`

**What happens:**
- Every concurrent request sees no rubric, parses the JD (paid), and tries to insert version 1.
- One wins; the others raise `IntegrityError`, which the user sees as `INTERNAL_ERROR`.

**Evidence:**
- 5 parallel requests against the same pasted JD → 1 completed, 4 × `UniqueViolationError`.

**Fix:**
- Take `pg_advisory_xact_lock` on the JD id around check-parse-insert, or catch `IntegrityError` and re-read the winning rubric.
- The lock also avoids paying for duplicate parses. This matters as soon as there is a batch-upload feature.

### 3. PII redaction changes what the model sees (high for quality, medium for privacy)

All of these are in [pii.py](../../backend/app/pipeline/pii.py) and are reproducible with `redact()`:

| Input | Output | Effect |
|---|---|---|
| `2019.01 - 2021.12` (dotted dates, plain hyphen) | `[PHONE]` | Job tenure is deleted, so years-of-experience criteria are graded blind. Seen in live prompts (product designer, nurse). 6 resumes. |
| `Ruby Castellanos` … `Ruby on Rails`, `Ruby` | `[CANDIDATE] on Rails`, `[CANDIDATE]` | The first-name pass erases a skill. The same happens with `Sydney` and `Austin` (the city disappears). |
| `José Hernández`, `Zoë Müller`, `Ana de la Cruz`, `Name: Priya Sharma` | unchanged | The name leaks to the LLM. 9 resumes. `_NAME_WORD` is ASCII-only and rejects particles and labels. |
| `José Hernández` / `Registered Nurse` (headline) | `José Hernández` / `[CANDIDATE]` | The detector falls through to the title line, erases the headline, then removes "Registered" everywhere. "Registered Nurse license" becomes "[CANDIDATE] Nurse license", which can flip a license knock-out. |
| `müller.12@examplemail.com` | `mü[EMAIL]` | The email regex is ASCII-only, so part of the address leaks. |
| `1 200 000 transactions`, `CTC 12 00 000` | `[PHONE]` | Metrics and salaries are erased. |
| `Senior Engineer, Acme` / `Built APIs` | `Built APIs` → `[CANDIDATE]` | Any 2–4 capitalised-word line in the first 5 lines can become "the name". |

**Fix:**
- Treat a digit run with a date shape (`\d{4}[./]\d{2}` or `\d{2}[./]\d{4}`, joined by `-`/`–`) as a date, not a phone number.
- Make `_NAME_WORD` Unicode-aware (`[^\W\d_]`) and allow lowercase particles.
- Accept a `Name:` prefix.
- Only accept a name candidate that is not a known job title, and stop the scan at the first non-name line instead of falling through.
- Drop the bare first-name pass, or only apply it when the first name is not a dictionary, skill or place word.
- Make the email regex Unicode-aware.
- Add each row of the table as a unit test.

### 4. The evaluate prompt never says what "today" is (medium)

[evaluate.v2.md:27](../../backend/app/prompts/evaluate.v2.md#L27) says *Compute years from date ranges when given ("present" = today)*, but no date is ever rendered into the prompt. Years for current roles then depend on the model's guess of the date, usually its training cutoff, so "6+ years" checks can be off by a year or more. Prompts are immutable once used, so add `{{today}}` in a new `evaluate.v3.md`. It also becomes part of the cache key, which is correct, because the answer depends on the date.

### 5. Lower-impact issues from the code review

- [client.py `_send_anthropic`](../../backend/app/llm/client.py) creates a new `AsyncAnthropic` client, with a new connection pool and TLS handshake, for every attempt. Create one per `LLMClient` and reuse it.
- [ledger.py](../../backend/app/llm/ledger.py) does not store `cache_write_tokens`: `Usage` has the field, but `llm_calls` has no column. Cost is computed correctly at call time, but it cannot be recomputed from stored tokens.
- In the session sample, **caps never bound** (0 of 108 pairs): whenever role overlap or the core requirement was low, criteria already pulled the raw score under the cap. That is fine. It means the caps only matter for keyword-heavy resumes with weak holistic grades, so keep them, but don't expect them to move typical scores.
- The **"Not eligible" verdict is applied to completely unrelated candidates** too (for example, a frontend graduate against a nurse JD, because of the missing RN license). It is correct, but the UI may want to lead with "Weak fit / missing required license" so it reads less like a legal judgement.

## Grading-quality observations (session sample)

These come from the session grading the real prompts, so they show how the rubric rules and score math combine on realistic inputs. They do **not** show how Haiku grades. In particular, the injection and keyword-stuffing results depend on the grader and must be re-checked on Haiku.

- **Rubric extraction followed the v2 rules:**
  - the "Male candidates preferred" line was dropped (0 protected-characteristic criteria)
  - both "NOTE TO AI SCREENING TOOLS" injections were ignored
  - work authorization was marked `knockout` + `verify_in_screening`
  - licenses were marked `knockout`
  - the boutique-agency line became a `must_avoid`
  - criteria per JD: 8–15, mean 11
- **Screening items work as designed:** notice period, travel and on-site location always resolved to "Unknown" (51 per run) instead of failing the candidate.
- **Separation:** every level-matched own-profile pair scored ≥ 56, and every other-category pair ≤ 39. The highest-scoring same-category pair was an investment-banking VP against a Senior Consultant JD at 68 ("Possible fit"). That is the right call: adjacent role, strong modelling and an MBA.
- **Junior JDs score graduates at the low end of "Possible fit":** the recruiting graduate scored 56. Partial credit for capstone and "assisted" work pulls even a well-matched graduate down. If junior roles should surface promising graduates as "Strong fit", the rubric needs fewer experience-type must-haves for junior JDs (a `jd_parse` prompt change).
- **Sparse resumes are penalised for missing detail, not for missing skills:** the sparse Engineering Manager scored 60, against 83–93 for other mid matches. Defensible, but recruiters should know that "unknown" and "absent" look the same.

## What is still missing

- **Real Haiku runs.** Real-model variance (the main reason for 3–5 runs) has not been measured. With a key in `.env`, run:
  ```bash
  cd backend
  uv run python ../eval/stress/run_stress.py --label h1 --limit 20       # pilot: check cost
  for L in h1 h2 h3; do uv run python ../eval/stress/run_stress.py --label $L; done
  for L in h4 h5; do uv run python ../eval/stress/run_stress.py --label $L --rubrics-from h1; done
  uv run python ../eval/stress/report.py h1 h2 h3 h4 h5 --out ../eval/stress/REPORT_haiku.md
  ```
  - **Estimated cost:** about $0.5–1.5 per 312-pair run at $0.10 / $0.50 per M tokens.
  - **What this run answers:**
    - rubric drift between parses (h1–h3 against each other)
    - evaluation-only noise (h1, h4, h5 share a rubric)
    - whether hidden-text injection or keyword stuffing moves Haiku's grades
- **Human calibration.** Expected bands here come from the generator's labels, not recruiters. Phase 4's `eval/cases` with recruiter-reviewed scores is still the real calibration.
- **Not covered:** scanned PDFs (OCR is Phase 5), non-Latin scripts (the PDF generator's font is Latin-1 only), the HTTP layer and UI under load.

## How to reproduce

```bash
cd backend
uv run python ../eval/stress/generate.py                                 # corpus (deterministic)
uv run python ../eval/stress/run_stress.py --label o1 --fake-llm          # one offline run, ~10 s
uv run python ../eval/stress/concurrency_probe.py --latency 3 --levels 5,10,15,20,40
uv run python ../eval/stress/report.py o1 o2 o3 o4 o5 --out ../eval/stress/REPORT_full_scale.md
```

The harness uses its own database (`jdscorer_stress`, created and migrated automatically) and storage folder (`backend/var/stress_storage`), so History in the app is untouched. The LLM response cache is forced off.

Session-provider answers for the 36-pair sample are in `backend/var/stress_manual_llm/`, which is git-ignored. Re-running `--model manual/claude-session --jds jd_003,jd_016,jd_023,jd_034,jd_041,jd_060,jd_066,jd_070,jd_083,jd_088,jd_090,jd_102` reuses them.
